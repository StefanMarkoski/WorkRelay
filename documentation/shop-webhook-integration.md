# WorkRelay order webhook: integration guide for the shop

This guide is for the developers of the shop (commerce app). It explains how the shop connects to WorkRelay and
sends order events so that every order appears in the right WorkRelay workspace, and only there.

- **New here? Start with [`shop-developer-guide.md`](./shop-developer-guide.md)**: what to build, what WorkRelay does with it, and who switches what on. This page is the full reference.
- Machine-readable schema: [`order-webhook.schema.json`](./order-webhook.schema.json)
- Optional customer signups: section 9, [`customer-webhook.schema.json`](./customer-webhook.schema.json)
- Optional products and stock: section 10, [`product-feed.schema.json`](./product-feed.schema.json)
- Base URL: `https://wayktzmupzrdcwosgnfg.supabase.co/functions/v1`

## 1. How the connection works

```
 Shop admin           WorkRelay (per tenant)                 Shop backend
     |  1. create connection  ->  secret key  wr_live_...  (shown once)
     |  2. paste the key into the shop's WorkRelay settings ------------>|
     |                                    3. POST /bind  {store_id}  <---|   (once)
     |                                    4. POST /order-webhook  <------|   (every order event)
```

1. A WorkRelay user of the tenant creates a connection under **Shops → Connect shop**. WorkRelay shows a
   **secret key** (`wr_live_` + 64 hex characters) **once**. It is stored only as a hash.
2. The shop admin pastes that key into the shop. Treat it like a password: server-side only, never in browser code,
   never in logs or URLs.
3. The shop calls **bind** once with its own **store id**. From then on that key works for that store only.
4. The shop sends **order events** to `/order-webhook` whenever an order is created or changes.

### What identifies what

| Concept | Where it comes from | Used for |
|---|---|---|
| **Tenant (organization)** | Resolved by WorkRelay from the **secret key**. Never from the payload. | Which workspace the order is stored in |
| **Store id** | Chosen by the shop (any stable string, up to 200 chars, e.g. the shop's own store/tenant id). Sent at bind and in `X-Store-Id` on every request. | Locks the key to one store |
| **Order id** (`order.external_id`) | The shop's own order id | Identity of the order. The same id always updates the same order |
| **Event id** (`event_id`) | Generated by the shop, unique per event | Idempotency: repeated deliveries are safe |

Any organization or tenant identifier inside the payload is ignored. A key bound to store `A` is rejected if it is
used with store id `B`, and a store id that is already connected to another WorkRelay connection cannot be bound twice.

## 2. Authentication

Every request carries:

```
Authorization: Bearer wr_live_<64 hex characters>
X-Store-Id: <your store id>          (order-webhook only; must equal the id given at bind)
Content-Type: application/json
```

Use HTTPS only. There is no request signature yet: the bearer key over TLS is the only credential, so keep it secret
and ask the WorkRelay tenant to **rotate** the key (Shops → the shop → General → Rotate key) if it may have leaked. A rotated key keeps the
store binding; update the shop with the new key.

## 3. Bind (once per connection)

`POST /bind`

```json
{
  "store_id": "shop-eu-001",
  "base_url": "https://shop.example.com"
}
```

- `store_id`: required, 1 to 200 characters. The id the shop will send in `X-Store-Id` forever.
- `base_url`: optional, must be `https`. For display and future features.

| Status | Body | Meaning |
|---|---|---|
| 200 | `{"status":"bound"}` | Bound now |
| 200 | `{"status":"already_bound"}` | Already bound to this same store id. Safe to repeat |
| 400 | `{"error":"invalid_payload","detail":"..."}` | Missing or invalid fields |
| 401 | `{"error":"invalid_key"}` | Unknown, malformed or revoked key |
| 403 | `{"error":"bound_to_another_store"}` | This key is already bound to a different store id |
| 409 | `{"error":"store_already_connected"}` | This store id is already connected to another connection |

## 4. Send order events

`POST /order-webhook`

### Event types

| `event_type` | Send when |
|---|---|
| `order.created` | An order is placed |
| `order.updated` | Any order data changes (items, totals, addresses, payment, fulfillment, notes) |
| `order.status_changed` | The order status changes |

Any other `event_type` is accepted but **ignored** (HTTP 202) and recorded as ignored.

### Envelope

| Field | Required | Type | Notes |
|---|---|---|---|
| `event_id` | **yes** | string, 1 to 200 | Unique per event. Reuse the same value when retrying the same event |
| `event_type` | **yes** | string | See the table above |
| `occurred_at` | **yes** | ISO 8601 date-time with `Z` or offset | When the change happened in the shop. Within the last 7 days and no more than a day ahead (see the note on times below). The examples carry sample dates: use the current time |
| `order` | **yes** | object | See below |

### The `order` object

Only `external_id` is required. **Everything else is optional**: send what you have.

| Field | Type | Notes |
|---|---|---|
| `external_id` | string, 1 to 200 | **Required.** The shop's order id |
| `order_number` | string, up to 100 | Human-facing number, e.g. `#1001` |
| `placed_at` | ISO 8601 date-time | When the customer placed the order. From 2000-01-01 to one day from now (see the note on times below) |
| `currency` | 3-letter code | e.g. `EUR`. Optional: if you leave it out, the order takes the currency the shop is set to in WorkRelay (see below) |
| `customer` | object | `name` (up to 200), `email` (valid email), `phone` (up to 64) |
| `totals` | object | `subtotal_minor`, `discount_minor`, `shipping_minor`, `tax_minor`, `total_minor`: **integers in minor units, never below zero** |
| `status` | string, 1 to 64 | Order status, see section 6 |
| `payment_status` | string, 1 to 64 | As reported by the shop |
| `fulfillment_status` | string, 1 to 64 | As reported by the shop |
| `billing_address`, `shipping_address` | object | `name`, `line1`, `line2`, `city`, `region`, `postal_code`, `country`, `phone` (all optional strings) |
| `items` | array, up to 1000 | Each: `external_id`, `sku`, `name`, `quantity` (integer 0 to 1,000,000), `unit_price_minor` (integer, never below zero) |
| `notes` | string, up to 5000 | Notes from the shop |

**Each shop has one currency.** The workspace sets it in WorkRelay when connecting the store (and can change it in the shop's details). It decides how
WorkRelay counts and reports that shop's money, and WorkRelay **never converts** between currencies.

- An order sent **without** a `currency` takes the shop's currency.
- An order sent **with the shop's currency** is used as it is.
- An order sent with a **different** currency is kept exactly as sent (nothing is relabelled, converted or dropped) and is marked on the order
  as a currency mismatch, so a misconfigured shop is easy to spot. Fix the shop or the payload and resend; the order is then clean.

**Money is always an integer in minor units**: `49.99 EUR` is `4999`. The minor unit follows the currency: `5000 JPY` is ¥5,000 (yen have no decimals) and `12500 KWD` is 12.500 KWD (three decimals). Decimal strings, floats and negative amounts are rejected: a refund is shown through `payment_status`, not as a negative total.

**Times must be real.** Every time you send must be an ISO 8601 date-time with an offset. `occurred_at` (when the event was sent) must be within the **last 7 days** and no more than **one day ahead**: events are live, and a week leaves room to re-send after an outage. The day ahead allows for a shop clock that runs fast. The other times (`placed_at`, `registered_at`, a product's `updated_at`) say when something really happened, so they may be older: from **2000-01-01** up to one day ahead. To import an old order, send the event now and put the real date in `placed_at`. Anything else is answered with `400` and the field's name, so a typo such as the year 3000 never reaches your order list or charts.
Unknown extra fields are ignored (the original payload is kept for diagnostics).

### Examples

A new order (send as much as you have):

```json
{
  "event_id": "ord_1001:created",
  "event_type": "order.created",
  "occurred_at": "2026-10-27T10:00:00Z",
  "order": {
    "external_id": "1001",
    "order_number": "#1001",
    "placed_at": "2026-10-27T10:00:00Z",
    "currency": "EUR",
    "customer": { "name": "Ana Petrova", "email": "ana@example.com", "phone": "+38970123456" },
    "totals": { "subtotal_minor": 4500, "discount_minor": 0, "shipping_minor": 499, "tax_minor": 0, "total_minor": 4999 },
    "status": "pending",
    "payment_status": "paid",
    "fulfillment_status": "unfulfilled",
    "shipping_address": { "name": "Ana Petrova", "line1": "Main St 1", "city": "Skopje", "postal_code": "1000", "country": "MK" },
    "items": [
      { "external_id": "line_1", "sku": "TEE-BLK-M", "name": "Black tee (M)", "quantity": 1, "unit_price_minor": 4500 }
    ]
  }
}
```

A status change (only the changed fields are needed):

```json
{
  "event_id": "ord_1001:status:completed:2026-10-27T12:30:00Z",
  "event_type": "order.status_changed",
  "occurred_at": "2026-10-27T12:30:00Z",
  "order": {
    "external_id": "1001",
    "status": "completed",
    "fulfillment_status": "shipped"
  }

```

An update that changes the note and clears the customer phone (`null` clears a field):

```json
{
  "event_id": "ord_1001:updated:2026-10-27T13:00:00Z",
  "event_type": "order.updated",
  "occurred_at": "2026-10-27T13:00:00Z",
  "order": {
    "external_id": "1001",
    "notes": "Leave at the door",
    "customer": { "phone": null }
  }
}
```

The smallest valid event:

```json
{
  "event_id": "ord_1002:created",
  "event_type": "order.created",
  "occurred_at": "2026-10-27T10:05:00Z",
  "order": { "external_id": "1002" }
}
```

## 5. How WorkRelay applies events

- **Absent field = unchanged. `null` = cleared.** A partial update never wipes fields it does not mention.
- **`customer` and `totals` merge per field.** Sending `customer: {"name": "Ana B"}` keeps the stored email.
- **`items` replaces the whole list** when present (send every line, not just the changed one). Omit `items` to leave them alone. `items: []` clears them.
- **Idempotent**: an `event_id` is processed once. A repeat of an already-processed event returns `{"status":"duplicate"}` and changes nothing.
  Do not reuse an `event_id` for a different change.
- **Order of arrival does not matter.** Each field is only overwritten by an event with a newer `occurred_at` than the
  one that last set it. A late, older event is recorded on the order's timeline as outdated and does not overwrite newer data.
  Make sure `occurred_at` reflects when the change happened in the shop.
- **Edits made in WorkRelay**: any member of the workspace can change an order's status, payment status and fulfillment status by hand. The edit is
  recorded on the order with the member who made it and is treated like an event that happened at that moment: a shop event with an older `occurred_at` is recorded as
  outdated and does not overwrite it, and a newer one replaces it. These edits are **not sent back to the shop**. The shop's own text stays
  visible on the order ("Store status"), so a difference between the two is easy to spot. A manual status change can start automations
  that listen for status changes (it never starts "new order" or "webhook" automations).
- **Customers**: WorkRelay's Customers page lists everyone who has placed an order. A customer is matched by the order's `customer.email`
  (ignoring upper/lower case and surrounding spaces), within your workspace, so the same address across two of your shops is one customer.
  Nothing extra needs to be sent. An order without an email still appears under Orders but does not create a customer.
- **Unknown order**: any event for an unseen `external_id` creates the order, so a missed `order.created` self-heals.
- **Automations**: `order.created` can trigger the tenant's new-order automations (for example a Discord notification), and a
  status change that was applied can trigger status automations. Replayed or duplicate events do not trigger one twice.
- **Data quality flags** shown on the order: `missing_currency` (amounts without a currency, and the shop has none set either), `currency_mismatch` (the order's currency differs from its shop's), `missing_total`,
  `no_items`, `no_customer_contact`. They never block ingestion.

## 6. Statuses

WorkRelay stores the shop's original text and maps it to its own set (case-insensitive; spaces and hyphens act as `_`).
Anything not listed maps to `unknown` (the original text is still stored and shown).

| Field | WorkRelay value ← accepted shop values |
|---|---|
| `status` | `pending` ← pending, new, open, awaiting_payment · `processing` ← processing, confirmed, in_progress · `completed` ← completed, complete, delivered, closed · `cancelled` ← cancelled, canceled, void |
| `payment_status` | `unpaid` ← unpaid, pending · `authorized` ← authorized · `paid` ← paid, captured, succeeded · `partially_refunded` · `refunded` · `failed` ← failed, declined |
| `fulfillment_status` | `unfulfilled` ← unfulfilled, pending, not_shipped · `partial` ← partial, partially_fulfilled · `fulfilled` ← fulfilled, shipped, delivered · `returned` |

If the shop uses other words, tell the WorkRelay team and the mapping can be extended.

## 7. Responses and retries

| Status | Body | What to do |
|---|---|---|
| 200 | `{"status":"processed"}` | Done |
| 200 | `{"status":"duplicate"}` | Already processed. Treat as success |
| 202 | `{"status":"ignored"}` | Unsupported `event_type`. Do not retry |
| 400 | `{"error":"invalid_payload","detail":"path: message; ..."}` | Fix the payload. Do not retry unchanged. The event is recorded as **failed** in WorkRelay; resending the same `event_id` with a corrected payload is accepted |
| 401 | `{"error":"invalid_key"}` | Wrong, malformed or revoked key |
| 403 | `{"error":"integration_not_bound"}` | Call `/bind` first |
| 403 | `{"error":"store_mismatch"}` | `X-Store-Id` does not equal the bound store id |
| 405 | `{"error":"method_not_allowed"}` | Use `POST` |
| 500 / 503 | `{"error":"internal_error"}` / `{"error":"conflict_retry"}` | **Retry** the same event (same `event_id`) with backoff |

Delivery guidance for the shop:

- Send an event **after** the order change is committed, and retry on network errors, timeouts and 5xx until you get a 2xx.
  Use exponential backoff (for example 5 s, 30 s, 2 min, 10 min, 1 h) with a sensible cap. WorkRelay does not pull from the shop
  and does not guarantee delivery on its own: **the shop must retry**.
- Keep a persistent outbox in the shop (an event table) so events survive restarts.
- Body size limit: about 1 MB per request. Send one event per request.
- Choose `event_id` so it is **stable across retries** and unique across events, for example
  `<order id>:<event>:<order version or updated_at>`.

## 8. Recommended behavior

- Send `order.created` once per order and `order.updated` for every later change. For `order.updated`, sending the
  **full order snapshot** is simplest and always correct; partial updates also work.
- Send `order.status_changed` in addition to (or instead of) `order.updated` when only the status changes.
- **Backfilling history**: send `order.created` for old orders with `occurred_at` set to the order's real time. Note that
  if the tenant has an automation for new orders turned on (for example a notification), each backfilled order will trigger it.
  Turn such automations off first.
- WorkRelay never writes back to the shop in this version, and it does not process payments, refunds or shipments.

## 9. Customer signups (optional)

Orders already create customers: WorkRelay's Customers page lists everyone who has placed an order. If the shop also wants to
tell WorkRelay about **accounts that were created before the first order** (for example to send a welcome message), it can use a second,
optional endpoint. Nothing here is required, and it does nothing until someone switches it on for the shop.

**Switching it on:** in WorkRelay, open **Shops**, open the shop, go to its **Customers** tab and turn on *Receive customer signups*.
It is off by default and per shop. While it is off, events sent to this endpoint are kept and shown as ignored in Event history.
If you resend the same event after switching it on, it is processed.

`POST /customer-webhook` with the **same key and the same `X-Store-Id`** as the order webhook (the key is already bound; there is no
second bind). One event per request, 1 MB at most.

```json
{
  "event_id": "cust_77:created",
  "event_type": "customer.created",
  "occurred_at": "2026-10-27T09:15:00Z",
  "customer": {
    "email": "ana@example.com",
    "name": "Ana Petrova",
    "phone": "+38970123456",
    "external_id": "cust_77",
    "registered_at": "2026-10-27T09:14:52Z"
  }
}
```

| Field | Required | Notes |
|---|---|---|
| `event_id` | **yes** | Unique per event; reuse it when retrying the same event. Same rules as orders |
| `event_type` | **yes** | `customer.created` or `customer.updated`. Anything else is accepted but ignored (HTTP 202) |
| `occurred_at` | **yes** | ISO 8601 with `Z` or an offset: when it happened in the shop |
| `customer.email` | **yes** | A valid address, up to 320. **This is how customers are matched**, with upper/lower case and surrounding spaces ignored |
| `customer.name` | no | Up to 200 |
| `customer.phone` | no | Up to 64 |
| `customer.external_id` | no | The shop's own id, up to 200. Stored and shown, **never used for matching** |
| `customer.registered_at` | no | When the account was created. Defaults to `occurred_at` |

Absent or `null` fields leave the stored value unchanged.

How WorkRelay treats these events:

- **One customer per email address**, across orders and signups and across all of the workspace's shops. A person who signs up and then
  orders is one customer; so is someone who ordered as a guest and registers later.
- **`customer.created`** records the signup, marks the person as registered, and can start a *customer signs up* automation
  (once per customer and shop; repeats and retries never notify twice).
- **`customer.updated`** only updates the profile (and marks the account as existing). It never starts a signup automation.
- **Older data never overwrites newer data**, the same rule as orders: send `occurred_at` as the time of the change in the shop.
- **Importing existing accounts**: signups that happened **before the feature was switched on** are saved but never notify anyone, so a
  bulk import does not flood the team. Their `registered_at` should be the real signup date.
- A **new customer's first order** is a separate automation (*a new customer places their first order*). It works from orders alone,
  so it is available to every shop, with or without this endpoint.
- People who signed up but have not ordered appear on the Customers page only when you choose *Registered only* or *All*.

| Status | Body | Meaning |
|---|---|---|
| 200 | `{"status":"processed"}` | Applied |
| 200 | `{"status":"duplicate"}` | Already processed. Treat as success |
| 202 | `{"status":"ignored","reason":"signups_disabled"}` | Customer signups are switched off for this shop. Switch them on in WorkRelay, then resend |
| 202 | `{"status":"ignored"}` | Unsupported `event_type`. Do not retry |
| 400 | `{"error":"invalid_payload","detail":"customer.email: ..."}` | Fix the payload (the detail names the field, never the value) |
| 401, 403, 405, 500 | as in section 7 | Same meaning and the same retry guidance |

Machine-readable schema: [`customer-webhook.schema.json`](./customer-webhook.schema.json).

## 10. Products and stock (optional)

WorkRelay's **Inventory** page lists your products and how many pieces are left, and can alert the team when a product runs low.
**The shop stays the source of truth**: WorkRelay shows the numbers you report and never changes them, and it does not subtract stock
when orders arrive. Nothing here is required. Products also appear on their own once an order contains an item with a `sku`
(with stock shown as "not reported" until the shop reports it).

There are two ways to report products. They use **the same data** and can be combined:

| | Who calls whom | Good for |
|---|---|---|
| **Push** | The shop sends `POST /inventory-webhook` when stock changes | Fast updates and fast low-stock alerts |
| **Pull** | WorkRelay calls a URL **on the shop** on a schedule and reads the answer | Shops that cannot push, and as a safety net behind push |

### The product feed

```json
{
  "products": [
    {
      "sku": "BIKE-ROAD-700",
      "name": "Road bike 700c",
      "stock": 12,
      "notify_on": 5,
      "price_minor": 89900,
      "currency": "EUR",
      "unit": "pcs",
      "category": "Bikes",
      "barcode": "3850123456789",
      "updated_at": "2026-10-30T09:15:00Z"
    },
    { "sku": "NAIL-100", "stock": 4800, "notify_on": 5000 }
  ]
}
```

Only **`sku` is required**. Everything else is optional, and an absent or `null` field **leaves the stored value unchanged**, so you can
send just `sku` and `stock` for a quick update. Fields you do not know about are ignored, so extra fields never cause an error.

| Field | Required | Notes |
|---|---|---|
| `sku` | **yes** | Up to 200. How a product is identified within a shop. Orders are matched to products by the same `sku` |
| `name` | no | Up to 300. Shown on Inventory. If missing, the SKU is shown |
| `stock` | no | Whole number of pieces on hand. `0` is a real value; leave it out (or `null`) if you do not know it |
| `notify_on` | no | Whole number, 0 or more. Your own low-stock threshold, see below |
| `price_minor` | no | Integer in the smallest currency unit, like orders. **Needs `currency`** |
| `currency` | with `price_minor` | Three letters, e.g. `EUR` |
| `unit` | no | Up to 50, e.g. `pcs`, `boxes` |
| `category`, `barcode` | no | Up to 200 and 100 |
| `updated_at` | no | ISO 8601 with `Z` or an offset: when this product last changed in the shop. Defaults to the moment WorkRelay received or requested the report. A time in the future is treated as now |

How WorkRelay uses it:

- **Newer wins, per product, for stock.** A stock report older than what WorkRelay already holds fills in anything missing but never
  overwrites, so a late retry or a slow pull cannot undo a more recent push. Sending the same report twice changes nothing.
- **Price: the latest sync wins.** A price you report is always taken, however the item is dated and whether the sync was a scheduled
  pull, Sync now or a push someone typed by hand; a sync that carries no price leaves the price alone. The price is shown "from the
  shop". If you never report one, WorkRelay shows the unit price from the product's most recent order line ("from orders"). If there is
  neither, no price is shown. Every price change is listed in **Inventory → Sync history** (before and after).
- **Notify on.** A product is *low* when its stock is **at or below** its notify-on number. The number can come from the shop
  (`notify_on`), or be typed in by hand on the Inventory page, and a hand-set number wins. A hand-set number is never changed by a
  report; entering 0 there removes it so the shop's number applies again. Different products can have very different numbers
  (bikes at 5, nails at 5,000). A product with no number never counts as low.
- **Low-stock alerts.** If the workspace has the automation *a product runs low on stock*, it fires **once** when a product becomes low,
  not on every report, and fires again only after the stock has gone back above the number. A product that is **already low the first time
  the shop reports it** alerts too, but with a cap so connecting a shop whose products are mostly low cannot flood a channel: up to **3 alerts per
  shop per 90 seconds** (the lowest stock first), and every other product in that sync arrives as **one summary message** ("5 more products in
  Game Store are already at or below their alert levels (A, B, C, …)"). Every one of them is marked low, so none alerts a second time.
  **Estimated stock (optional).** A shop that has *Estimate stock between syncs* switched on also alerts before it reports again, with the same
  automation: nothing more to switch on. The estimate is the last reported stock minus the pieces ordered since, leaving out **cancelled** orders and orders whose `fulfillment_status` is
  **`returned`** (they give their pieces back; a partial return cannot be expressed, so send `returned` only when the whole order came back). It alerts once when the orders take
  it to the alert level, is re-armed by a cancellation or a return that lifts it back above the level, and is started over by every report from the shop. A
  product that is already low by the shop's own number is not announced twice. The estimate is checked once at the end of each order, so an order that takes many products to their level at once sends up to **3 single alerts per shop per 90 seconds** and one summary for the rest, and an order the shop later edits to other products re-arms the ones it lost. Every low-stock message ends with its **Source**: the shop's name
  for a number the shop reported, or *WorkRelay (estimated for <shop>)* for an estimate.
- **Failures.** An event WorkRelay could not accept, and an automation run that failed, are listed under **Failures** with a plain explanation. They are kept for 90 days by default; an owner or admin sets 1 to 365 days under **Settings → Failures**, and the failures already older than that are removed the moment you save, and later ones as they age (events that went through and runs that succeeded are never removed by this).
- **Event history.** Every push and every scheduled pull appears under **Shops → Event history** as `inventory.push` or
  `inventory.pull`, with a short summary (how many products, never the products themselves), so you can see that a feed arrived, was
  rejected or failed, and why. These entries are kept for 30 days.
- **No deleting.** Products are never removed by a report. A product you stop sending simply keeps its last numbers.

### Push: `POST /inventory-webhook`

Same key and the same `X-Store-Id` as the order webhook (the key is already bound; there is no second bind). The body is the feed above:
**up to 500 products and 1 MB per request.**

**Nothing to switch on.** Any connected shop can push at any time and as often as it likes; there is no per-shop switch and no limit. The calls per days that WorkRelay sets (**Shops → the shop → Inventory**) only limit WorkRelay's own calls to your products endpoint.

```bash
curl -s -X POST "$BASE/inventory-webhook" -H "Authorization: Bearer $KEY" -H "X-Store-Id: $STORE" \
  -H "Content-Type: application/json" \
  -d '{"products":[{"sku":"BIKE-ROAD-700","stock":11}]}'
```

| Status | Body | Meaning |
|---|---|---|
| 200 | `{"status":"processed","applied":2}` | Applied. `applied` is the number of products in the request |
| 400 | `{"error":"invalid_payload","detail":"products.0.stock: ..."}` | Fix the payload (the detail names the field, never the value). The whole request is rejected |
| 401, 403, 405, 500 | as in section 7 | Same meaning and the same retry guidance |

There is no `event_id`: reports are safe to repeat, so on a network error or 5xx simply send the same report again.

**Telling the team who synced (optional).** One optional field can sit next to `products` in the push body:

| Field | Notes |
|---|---|
| `synced_by` | `{"name":"Marko","role":"Admin"}`: who pressed the sync button in your admin. Both parts are optional (up to 120 and 60 characters) |

Every push that was applied can start the workspace's **a shop syncs its products** automation. Whether it does is the team's choice in WorkRelay (the automation, and which shops it covers), never something the shop sets in the request. The automation, whose message reads *"Marko (Admin) has synced their products (Game Store)"*.
Without `synced_by` the message names the shop instead. Requests from the same shop and the same person that arrive close together (each within 90 seconds of the one before), such as the chunks of one big sync,
are announced **once**. A request after 90 seconds of quiet is a new sync and is announced again. Scheduled checks and Sync now from inside WorkRelay never announce.

Every applied push also updates the shop's **"Synced 12m ago"** line on the Inventory page, with `synced_by` shown as who sent it, and appears in the Live feed on the Overview.

### Pull: WorkRelay calls the shop

On the shop's **Inventory** tab, the workspace enters, per shop, the **Products URL** and, if the endpoint needs it, an **Authorization**
value. WorkRelay then requests the URL on a schedule:

```
GET https://yourshop.com/workrelay/products
Accept: application/json
Authorization: Bearer abc123        (only if one was entered)
```

The shop answers `200` (any `2xx`) with the feed above, either `{"products":[...]}` or just the list `[...]`. The answer is the full
catalogue, or at least every product whose stock should be kept current.

- **How often is set by WorkRelay**, per shop, as *calls per number of days* (for example 15 calls per day is about one call every
  1 hour 36 minutes, 200 per week about every 50 minutes). It is shown read-only on Shops → the shop → Inventory. The fastest possible is one
  call every 5 minutes. A call that fails still counts, and is not retried before the next scheduled time.
- **Limits:** up to **5,000 products and 5 MB** per answer, **15 seconds** to respond. Larger catalogues are not supported yet.
- **Safety rules:** the URL must be `https`, must resolve to a public address (no private networks or `localhost`), and **redirects are not
  followed** (a 3xx counts as a failure; give the final URL). The Authorization value is stored privately, never shown again after saving, and
  sent only to that URL.
- **Timestamps:** each product is stamped with the moment WorkRelay *sent* the request unless it carries its own `updated_at`, so a push
  that happened while the answer was on its way is not overwritten.
- **Failures** (non-2xx, not JSON, wrong shape, timeout) appear as *The last check failed: ...* on Shops → the shop → Inventory, and nothing from
  that answer is applied.
- A schedule can be paused per shop. If no schedule has been set for a shop, WorkRelay does not call it; ask WorkRelay to set one.

Machine-readable schema: [`product-feed.schema.json`](./product-feed.schema.json) (the pull answer may hold up to 5,000 products, a push up to 500).

### Write-back: WorkRelay tells your shop its stock number (optional)

Off by default, and switched on per shop by the **workspace owner**. When it is on and an order, a cancellation or a return changes WorkRelay's
estimate for a product, WorkRelay sends your shop the new number for that product. It needs *Estimate stock between syncs* switched on, because the
estimate is the number that is sent.

- **What is sent:** the SKU and the new absolute stock number, with a sequence number, a time, and the number WorkRelay last read from your shop for
  that SKU (and when). Never a difference, so a repeat changes nothing. Never a name, an email, a price or anything about the customer. An estimate
  below zero is not sent.
- **WorkRelay reads your shop first, like `git pull` before `git push`.** Write-back needs the shop's **product feed address** (section 10, "Pull"):
  before WorkRelay sends a number it reads your shop's own numbers from that address, quietly (no notification, no "synced" announcement; it
  shows in Sync history as a read before sending), and reads them once more after a push to check your shop took the numbers. If your shop cannot
  be read, nothing is sent. If your own number differs from what WorkRelay believes your shop holds (for example you restocked), WorkRelay does
  not overwrite it: it opens a conflict and the owner decides (see below).
- **The read can be narrow.** WorkRelay may add `?skus=SKU1,SKU2,...` (comma-separated, URL-encoded, at most 100 SKUs) to your product feed address and
  read it for just those products. **Support is optional:** if your feed answers with only those SKUs, WorkRelay notices and keeps asking that way
  (it is cheaper for both of you); if your feed ignores the parameter and answers with everything, WorkRelay notices that too and reads the whole feed
  (it asks again once a week in case you add it). Either answer is correct. A number is only sent for a SKU that was in an answer WorkRelay got, so a
  SKU your feed does not list is not sent to.
- **Reads have a budget.** Reads before and after sending have their own hourly limit per shop (60 by default; only WorkRelay's platform admin can change
  it), separate from how often WorkRelay reads your feed on a schedule. When it is reached, numbers wait for the next hour.
- **Set up in WorkRelay** (Shops → the shop → Inventory): the product feed address, the shop's public **https stock address** (the standard port 443, no
  login in the address, and no secret in it either: the signature is the secret), a **signing secret** (`wr_sign_…`, shown once), then
  **Send test**, then the switch. Changing the address or the secret switches write-back off until the shop passes a new test.
- **Turning it off in WorkRelay stops everything**, even if your shop is ready to receive: nothing queued is sent afterwards, and the check is made
  again just before each request leaves. Any member of the workspace can switch it off. The one exception is a number the owner chose in a conflict ("send WorkRelay's"): it is kept and goes out, after the shop has been read, once write-back
  is switched on again, and lapses after 7 days. Numbers WorkRelay calculated itself are dropped.

WorkRelay sends `POST <your stock address>` with `Content-Type: application/json` and these headers:

| Header | Value |
|---|---|
| `X-WorkRelay-Timestamp` | Unix seconds when WorkRelay signed the request |
| `X-WorkRelay-Request-Id` | A UUID, new for every request (a retry gets a new one) |
| `X-WorkRelay-Signature` | `v1=` followed by the hex HMAC-SHA256 of `timestamp + "." + request id + "." + the raw body`, keyed with your signing secret |

```json
{
  "type": "stock.update",
  "request_id": "7d6c1f0e-2f4b-4b6e-9f4a-3c9f8f1d2a10",
  "sent_at": "2026-10-31T12:00:00.000Z",
  "store_id": "shop-eu-001",
  "items": [
    { "sku": "TEE-BLK-M", "stock": 7, "seq": 412, "as_of": "2026-10-31T11:59:58.120Z", "reported_stock": 9, "reported_at": "2026-10-31T11:59:41.000Z" },
    { "sku": "MUG-WHITE", "stock": 11, "seq": 413, "as_of": "2026-10-31T11:59:58.120Z", "reported_stock": 11, "reported_at": "2026-10-31T11:59:41.000Z" }
  ]
}
```

`stock` is the number WorkRelay wants your shop to hold. `reported_stock` and `reported_at` are the number WorkRelay last read from your shop for that
SKU, and when (`null` if it never did). If your shop's own number has moved since `reported_at` by something WorkRelay cannot know about, such as a
restock or a manual correction, **do not apply the number**: leave your stock as it is, and WorkRelay will see the difference on its next read and ask the
owner.

If the workspace owner has switched on **WorkRelay keeps the stock** for your shop (for a shop that does not count its own stock), the rule is the
other way round: WorkRelay's number is the one that stands, so **apply `stock` every time**. `reported_stock` is then only what your shop said when
WorkRelay last read it, and a difference from it is not a problem. Your shop's own number is still read, and is shown to the owner in Sync history, but
it never replaces WorkRelay's.

**Verify every request before you act on it.** Anyone who finds the address can send a request; only WorkRelay can sign one. Check the signature with
a constant-time comparison, reject a timestamp more than 5 minutes from your clock, and ignore a `request_id` you have already seen.

```js
// Node.js. `headers` has lower-case names; `rawBody` is the body exactly as it arrived (do not parse and re-serialize it).
function verifyWorkRelay(secret, headers, rawBody) {
  const crypto = require('crypto')
  const ts = headers['x-workrelay-timestamp']
  if (!ts || Math.abs(Date.now() / 1000 - Number(ts)) > 300) return false
  const expected = 'v1=' + crypto.createHmac('sha256', secret)
    .update(ts + '.' + headers['x-workrelay-request-id'] + '.' + rawBody).digest('hex')
  const given = String(headers['x-workrelay-signature'] || '')
  return given.length === expected.length && crypto.timingSafeEqual(Buffer.from(given), Buffer.from(expected))
}
```

```php
<?php
// PHP. $rawBody is file_get_contents('php://input'); header names are as PHP gives them.
function verifyWorkRelay(string $secret, array $headers, string $rawBody): bool {
    $ts = $headers['X-WorkRelay-Timestamp'] ?? '';
    if ($ts === '' || abs(time() - (int) $ts) > 300) return false;
    $expected = 'v1=' . hash_hmac('sha256', $ts . '.' . ($headers['X-WorkRelay-Request-Id'] ?? '') . '.' . $rawBody, $secret);
    return hash_equals($expected, $headers['X-WorkRelay-Signature'] ?? '');
}
```

- **The test.** *Send test* posts a signed `stock.test` request with a random `challenge`. Your endpoint passes by verifying the signature and
  answering `200` with JSON `{"challenge": "<the same value>"}`. It then sends a second `stock.test` request with a **wrong signature**, which your
  endpoint must refuse with `401` or `403`. An endpoint that accepts anything, or that echoes the challenge without checking the signature,
  cannot pass: otherwise anyone who finds the address could set your shop's stock.

```json
{
  "type": "stock.test",
  "request_id": "0b8a2c64-6c6e-4a43-8a52-5f0d7f6a9b11",
  "sent_at": "2026-10-31T12:00:00.000Z",
  "store_id": "shop-eu-001",
  "challenge": "9f2c4d1e7a8b4c3d9e0f1a2b3c4d5e6f"
}
```

- **Answering.** Any `2xx` means accepted. Anything else, a timeout (10 seconds) or a redirect (never followed) is a failure: each SKU is tried again
  1 minute and then 5 minutes later, then given up on. **5 failed requests in a row switch write-back off by itself** (a failed read of your feed
  counts too), and the reason is shown next to the switch. Answer quickly and do the work after answering. A request carries up to 100 SKUs and
  the answer covers all of them, so **answer `2xx` and ignore a SKU you do not know**. If you answer a request with several SKUs with a `4xx`
  (other than `408` or `429`), WorkRelay does not give up on all of them: it sends the numbers again **one at a time**, so only a SKU you refuse
  on its own is given up on (it is not retried, and counts as a failed request).
- **Order and repeats.** A request carries up to 100 SKUs, at most 20 requests a minute, and one at a time per shop. Apply a number only if its `seq`
  is higher than the one you last applied for that SKU; a lower one is an older number that arrived late.
- **When the numbers disagree.** If the numbers WorkRelay reads from your shop differ from what WorkRelay believes your shop holds (what it last
  sent, less what sold since), nothing is overwritten and nothing more is sent for that product. WorkRelay first waits about 90 seconds and judges the
  difference again, because an order your shop has already counted may still be on its way to WorkRelay (send order events promptly); only a
  difference that is still there then is shown to the owner. WorkRelay records both numbers and the
  difference, and the owner chooses: keep the shop's number, or send WorkRelay's. The disagreement and the decision stay in Sync history, which shows
  both directions: what your shop reported to WorkRelay, and what WorkRelay sent to your shop.
- **Your own safeguards.** Allow-list WorkRelay's requests by signature, not by IP address. Keep the signing secret out of your repository. If it leaks,
  press *Replace secret* in WorkRelay: the old one stops working at once.

BASE=https://wayktzmupzrdcwosgnfg.supabase.co/functions/v1

### Go-live checklist

- [ ] Key stored server-side only; not in logs, URLs, browser code or the repository
- [ ] Bind succeeded (`bound` or `already_bound`); `X-Store-Id` identical on every request
- [ ] `occurred_at` is the time of the change in the shop, in ISO 8601 with `Z` or an offset
- [ ] Money sent as integer minor units (never negative: a refund is a `payment_status`), in the shop's currency (send `currency`, or leave it out and rely on the shop's setting in WorkRelay)
- [ ] Events carry stable, unique `event_id` values; retries reuse the same id
- [ ] A persistent outbox retries on network errors and 5xx
- [ ] 4xx responses are logged (the `detail` field says what to fix) and not retried unchanged
- [ ] A test order shows up under Orders with the right totals, items and statuses
- [ ] (Products, optional) a test product shows up under Inventory, and a second report with the same values changes nothing

## 12. Troubleshooting

| Symptom | Likely cause |
|---|---|
| 401 `invalid_key` | Key truncated, wrong environment, or rotated/revoked |
| 403 `integration_not_bound` | `/bind` was never called for this key |
| 403 `store_mismatch` | `X-Store-Id` differs from the id used at bind |
| 400 mentions `occurred_at` | Not ISO 8601 (for example a Unix timestamp or a date without time) |
| 400 mentions `total_minor` etc. | A decimal or string was sent instead of an integer |
| Order shows a currency badge such as "USD, not MKD" | The order's `currency` differs from the one the shop is set to in WorkRelay. Correct the payload or the shop's currency; nothing was converted |
| Order shows "Incomplete data" | No currency, total, items or customer contact was sent (informational) |
| Status shows `unknown` | The shop's status word is not in the table in section 6 |
| Order did not update | The event was older than data already stored, or the `event_id` was a duplicate. Check the timeline and Event history |

## 9. Reading data back (export)

A shop can read its own orders, customers and products back through `GET /export/{orders|customers|products}`: read-only, signed with a separate export secret the workspace owner creates, 120 calls an hour, paged by cursor. How to sign a request, the paging and the status codes are in section 8 of the [developer's guide](./shop-developer-guide.md).
